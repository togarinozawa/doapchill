# ドパチル ver.1

ドーパミン依存的なスマホ使用習慣からの立ち直りを支援する、個人用のアプリ使用制限アプリ。

- 対象: Android 10 (API 29) 以上 / targetSdk 36 (Android 16)
- 配布: 個人用サイドロード
- パッケージ名: `com.dopachiru`

### 対応バージョンの決めかた

手持ちで一番古い **AQUOS R2 SH-03K** が
[2020年3月の更新で Android 10 に上がったきり打ち止め](https://k-tai.sharp.co.jp/support/osv/docomo/osv10/index.html)
なので、そこに合わせて **API 29** にしてあります。
**dtab Compact d-42A** は Android 11 出荷・
[2022年11月に Android 12](https://www.docomo.ne.jp/support/product_update/d42a/20221101.html)
なので、更新の当たっていない 11 のままでも入ります。

古い端末に向けて振る舞いを変えているのは1か所だけです。

| | 効く範囲 | 古い端末での扱い |
|---|---|---|
| `foregroundServiceType="specialUse"` | Android 14 以降 | 型を渡さずに常駐する(14 未満は型の指定自体が不要) |
| `<property>` / `dataExtractionRules` | Android 12 以降 | 端末が知らない要素として読み飛ばされる。`allowBackup="false"` は全バージョンで効く |
| `POST_NOTIFICATIONS` | Android 13 以降 | 要求しない(古い端末では通知は既定で出る) |

さらに下げるときに効いてくるもの:

- **API 29 未満** — `AppOpsManager.unsafeCheckOpNoThrow` が無い(使用状況の許可判定)。旧 `checkOpNoThrow` で代替できる
- **API 26 未満** — `core` が使う `java.time` に脱糖(desugaring)が要る

## ビルドと導入

### 必要なもの(このリポジトリの環境では導入済み)

| | 場所 |
|---|---|
| JDK 21 (Temurin) | `C:\Program Files\Eclipse Adoptium\jdk-21.0.12.8-hotspot` |
| Android SDK | `C:\Users\hai\soft\android-sdk` (platform-tools / android-36 / build-tools 36.0.0) |
| Gradle | wrapper 同梱 (8.14.5) |

### ビルド

```bash
./gradlew :app:assembleDebug
```

APK は `app/build/outputs/apk/debug/app-debug.apk` に出ます。

### 端末に入れる

USB デバッグを有効にした端末を繋いで、次を実行するとインストールと
「制限された設定」の解除まで通しでやります。

```bash
./install.ps1
```

手でやる場合:

```bash
./gradlew :app:dist
adb install -r dist/dopachiru-0.9.0.apk
```

### 配布用 APK

**[Releases](https://github.com/togarinozawa/doapchill/releases) から落とせます。**

> `dist/` は [.gitignore](.gitignore) に入っているので、**clone しても APK は付いてきません。**
> リポジトリの中を探しても無いのが正しい状態です。配布物は Releases 側にあります。

```bash
./gradlew :app:dist        # dist/dopachiru-<版>.apk
./gradlew :desktop:packageSetup      # dist/dopachiru-windows-<版>-setup.zip
./gradlew :desktop:packagePortable   # dist/dopachiru-windows-<版>.zip
```

`dist/` に版つきで出ます。`app/build/outputs/apk/release/app-release.apk` は
版が名前に入らず次のビルドで黙って上書きされるので、渡すものはこちらを使います。

R8 で圧縮した版が既定です。条件・アクションの実装とシリアライザ
(`ConditionNode` / `Gate` の各サブタイプの `$$serializer` と `Companion`)が
難読化も削除もされずに残っていることは mapping.txt で確認済みです。
圧縮が原因かを切り分けたいときは `-PnoMinify=true` を付けてビルドします。

> Play ストアに出さないので debug キーストアで署名しています。
> 同じ鍵で署名し続けるかぎり、アンインストールせずに上書き更新できます。

### ⚠ 導入時にほぼ確実に詰まるところ(Android 13 以降のみ)

**Android 13 以降、ストア以外から入れたアプリはユーザー補助(Accessibility)を有効にできません。**
設定画面でスイッチが灰色になり、押しても反応しません。

> Android 12 以前(SH-03K・d-42A はどちらもここ)にこの制限はありません。
> 設定 → ユーザー補助 から普通に ON にできるので、以下は読み飛ばして構いません。

adb が使えるなら、これが一番速い:

```bash
adb shell appops set com.dopachiru ACCESS_RESTRICTED_SETTINGS allow
```

端末だけで済ませる場合:

1. 設定 → ユーザー補助 → ドパチル のスイッチを押して**わざとブロックされる**(これをやらないと次のメニューが出ない)
2. 設定 → アプリ → ドパチル → 右上「⋮」→「制限された設定を許可」
3. 画面ロックで認証

そのうえで、設定 → ユーザー補助 → ドパチル を ON にします。

### 入らないとき

古い端末で **「エラーが発生してアプリがインストールできませんでした」** が出ることがあります。
たいていは **Google Play プロテクト**が止めています。

> 「Play にないアプリなので通報しますか?」も同じ仕組みです。
> **これは端末の機能ではなく、Google Play 開発者サービスに入っている Google のスキャナ**です。
> 自分の端末で自分のアプリを入れるだけでも、既定では毎回これに聞かれます。切れます。

**Play ストア → 右上のアイコン → Play プロテクト → 歯車 → 「アプリのスキャン」を OFF**

それでも入らないときは、次の順に疑ってください。

| 症状 | 原因 | 対処 |
|---|---|---|
| 入れた直後に消える・失敗する | Play プロテクト | 上のスキャンを切る |
| 「アプリがインストールされていません」 | **署名の食い違い**。前に別の鍵で署名した版が入っている | 古いほうを**アンインストールしてから**入れる |
| ブラウザからの導入で止まる | そのブラウザに「不明なアプリのインストール」が許可されていない | 設定 → アプリ → そのブラウザ → 不明なアプリのインストール → 許可 |
| そもそも一覧に出ない | Android 9 以下 | **minSdk は 29(Android 10)** です |

**理由を確実に知りたいなら adb が一番早い**です。失敗の種類がそのまま出ます。

```bash
adb install -r dist/dopachiru-0.9.0.apk
```

`INSTALL_FAILED_VERIFICATION_FAILURE` なら Play プロテクト、
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` なら署名の食い違いです。

### 入っている版を確かめる

**設定タブの一番下**に出ています(`ドパチル 0.9.0 (16)`)。
括弧の中は versionCode で、表向きの版が同じでも作り直したものかを見分けられます。

gradle の値を焼き込むのではなく**入っているパッケージから読んでいる**ので、
渡した APK と端末の中身が食い違っていても、画面は嘘をつきません。

### そのほかの初期設定

アプリ内の「設定」タブに、必要な権限のチェックリストがあります。

- ユーザー補助の有効化(必須。これが無いと何も検知しません)
- 電池の最適化から除外(常駐が落とされにくくなる)
- 通知の許可(初回起動時に聞かれる。常駐通知に使う)

### 見張りが外れたら知らせる

取り締まりのほとんどはユーザー補助の上に乗っています。これを切られると、アプリは
起動していても**何も止めません**。いちばん危ないのは、切ったこと自体を忘れて
「守られているつもり」で過ごすことです ── 誘惑に負けて切ったのなら、なおさら。

そこで、**一度許可したユーザー補助・重ね表示の許可が外れたら**、常駐サービス
([PermissionGuard])が目に入る強さの通知で知らせます。タップすると外れているほうの
設定へ直行します。ユーザー補助が切られると本体のサービスは死にますが、この常駐は
生き残るので、「切られたこと」に気づける場所はここだけです。

> **入れたてでまだ許可していない段階では鳴りません。** 一度許可したものが「消えた」
> ときだけです。設定を促す案内と区別がつかなくなるのを避けるためで、許可した事実は
> 端末に残すので、プロセスが作り直されても判断がぶれません。

## 集中モード

思い立った瞬間に始めて、時間が来たら勝手に解ける一時的な封鎖です。
ルールが「いつ・どの条件で」を先に決めておくものなのに対して、こちらはその場かぎり。
食事のあいだだけ手を止めたい、のような使い方のためのものです。

### 止める仕組みは罰と同じ

実体は罰と同じ `Lockout` です。判定も保存も期限切れも同じ道を通ります。
違うのは **`earlyExit` が入っていること**だけで、そこが罰との分かれ目になります。

| | 罰 | 集中 |
|---|---|---|
| 始まり | ルールを破ったとき | 自分で押したとき |
| 出口 | **無し**。時間が来るまで開かない | 手間 + ポイント |
| 画面 | 「押し切る手段はありません」 | 「足せる・切り上げられる」 |

同じ仕組みで動かしながら**画面に出す約束が正反対**なので、
ここを取り違えるとどちらかの画面が嘘をつきます。`earlyExit` の有無1つで分けています。

### 短く始めて足す

既定は15分と短めです。**長く始めすぎたときの逃げ方が高くつく**ためで、
30分で始めて20分で用が済むと、残りを解くのに手間とポイントを払うことになります。
悪いことをしていないのに罰されている感じになるので、
短く始めて足りなければ足すほうが素直です。長さは5分刻み。

**押し間違いは最初の1分だけ無料で取り消せます。** ホーム画面に置いたボタンは押し間違えるので、
そこまで有料にすると置くこと自体が怖くなります。

### 止める範囲を選べる

集中は「逃がすもの以外ぜんぶ」の一択ではありません。用途で止めたい範囲が違うので、
**型(テンプレ)**として先に決めておけます([FocusTemplate] / [FocusScope])。

| 範囲 | 意味 | 例 |
|---|---|---|
| このグループだけ | そのタグのアプリだけ止める | 「SNS だけ1時間」 |
| このグループ以外 | そのタグ以外を止める(許可リスト型) | 「仕事アプリ以外を止める」 |
| 逃がすもの以外ぜんぶ | 端末ごと閉める。いちばん強い | 「全部止める」 |

範囲は `Target`(タグ/例外)そのものではなく **scope + タグ** で持ちます。タグの中身
(どのアプリが属すか)が後から変わっても、型は同じ意味で効いてほしいためで、
実際の `Target` は始める瞬間に組みます。設定 → 集中モードで作り、ホームに置けます。

### 入口

- **型のショートカット** — 上の型を1つずつホーム画面に置けます。1タップで決め打ちの長さ、
  または押してから長さを選ぶ、のどちらかを型ごとに選べます
- **「長さを選ぶ」** — 押すと5分刻みの格子(5〜150分、5列×6行)が出て、その場で長さを
  決められます。ボタン1つで足ります。型を指していれば、その範囲で止まります
- **1タップボタン** — 長さを決め打ちしたもの。ドパチルを開いてから始めるのでは遅い
  (そのときにはもうスマホを握っている)ので、選ぶ手間すら惜しいとき用
- **アプリのアイコンを長押し** — 「長さを選ぶ」と 15分/30分 の候補が出ます
- **ダッシュボードのカード** — 長さを選んで始める

集中中に入口を押すと、始め直さずに**残り時間と足すボタン**だけが出ます。
押し間違いで長さが化けるのがいちばん困るので。走る集中は1つだけです。

> Windows でも範囲を選んで始められます(設定 → 集中モード)。ホーム画面の
> ショートカットは Windows には無いので、始めるのは設定画面からになります。

### 閉じ込めは起きません

電話・緊急発信・ホーム・設定はルールより強い床(`ProtectedApps`)で常に開いています。
音楽や時計などを追加で逃がすことも設定できます。
時間が来れば必ず解けるので、ポイントが尽きても閉じ込められることはありません。

**完走すると加点します。** 長さに比例させていないのは、5分を12回に割って稼げてしまうと
集中そのものではなく数を稼ぐ遊びになるためです。

> 集中モードそのものはまだ端末をまたぎません(ルールと実績が先)。
> `Lockout` に `uid` を持たせてあるので、あとから同じ仕組みに載せられます。

## 予約 — 使う時間を先に決めておく

「この時間だけ使う」と**冷静なうちに**枠を取っておく仕組みです。開いた瞬間に
「何分使う」と決める宣言([DeclareAction])は、そのときすでに欲求が立ち上がって
います。予約はその手前 ── 使いたくなる前に枠を取り、外では塞ぎます。
Sticky Goals(Lee ら, CHI 2021)の事前コミットメントにあたります。

**直前予約は取れません。** いまから既定で1時間より手前には置けない(設定で変えられる)。
「いま開きたいから今すぐ予約」では冷静な決定にならないので、少し先にしか
置けないようにしてあります。だからカレンダーに書くように「よし、この時間で
済ませる」と予定にできます。

- 条件 `outside_reservation` を完全封印と組むと、**予約した枠でしか開けない**アプリになります
- 予約は罰ではないので、**枠を流しても損しません**(ACDP #7 Playing by Appointment を避ける)
- ダッシュボードの「予約」カード(Android)/ 設定 → 予約(Windows)から取れます

> 予約は端末ごとに持ちます(まだ同期しません)。集中と同じく、あとから載せられます。

## 開く癖・脱線を狙う4つの介入

アプリ全体ではなく「その中のどの面か」「どう使うか」を狙うもの。合計時間の
上限より、**引き金そのもの**に効きます(Cho ら CSCW 2021 / Lukoff ら CHI 2021)。

| 介入 | 何をするか | 根拠 |
|---|---|---|
| **ショート/リールだけ塞ぐ**(`on_screen`) | アプリの中のショート・リールの画面に入った瞬間だけ塞ぐ | 短尺×推薦が最もラビットホール化する。始まってから止めるのはほぼ効かない |
| **音だけにする**(`radio`) | 映像を覆い、音は流したまま。覗くには手間 | 無関係な推薦は100%が制御感を下げる ── 意志で無視せず視界から外す |
| **目的を書かせる**(`intention`) | 開くとき「何をしに開いた」を書かせ、隅に出し続ける | 実行意図は脱線防止で最大(d=0.77) |
| **前回から間をあける**(`cooldown_since_use`) | 一度使ったら次までN時間あける | 反射的な開き直しを、間隔を空けて断つ |

> **`on_screen` の脆さ**: アプリ内の画面判定は、Android のノードツリーの
> resource-id を頼りにしています(`SCREEN_MARKERS`)。**アプリの更新で
> 変わりうる**もので、取れなくなったら塞ぎ続けるのではなく**素通しに倒れます**。
> ブラウザ版のショートは URL(`youtube.com/shorts`)で取れるので、そちらは頑丈です。
> Windows のアプリ内画面判定は手立てが無いので、ブラウザの URL 側だけが効きます。

## 端末間の同期

**既定で切ってあります。** 設定タブで住所・合言葉・端末名を入れて初めて動きます。
サーバーは [server/worker](server/worker/README.md)(Cloudflare Workers + D1)。

### 配るだけで、取り締まりには関わりません

判定はすべて端末の中です。**サーバーが落ちていても、圏外でも、機内モードでも
縛りは効いたまま**で、止まって起きるのは「別の端末で足したルールがまだ届かない」だけ。

逆に言えば、**判定を通信の向こうに置いてはいけません。**
ネットを切れば外れる制限は、機内モードにするだけで抜けられる制限です。

### 何が出て、何が出ないか

| 出る | 出ない |
|---|---|
| ルール(反省文を含む) | どの瞬間に何を見ていたか |
| タグ | ゲート |
| アプリ名 | 変更リクエスト |
| 1日ごとの使用時間 | 押し切りの記録の中身 |

**ゲートと変更リクエストを配らない**のは、承認待ちが別の端末に流れると
**片方で作った申請をもう片方で承認できてしまう**からです。ゲートを置いた意味が消えます。

### 仕組み

**毎回まるごと送ります。** 「前回から変わったぶんだけ」を端末側でやると、
取りこぼしたときに二度と送られないバグが出ます。数個のルールなら数キロバイトなので、
全部送って古いものはサーバーに捨てさせます
(`ON CONFLICT ... WHERE excluded.updated_at > ...`)。

**受け取るほうはサーバーが振る `rev` をカーソルにします。**
端末の時計に頼らないので、時計がずれていても取りこぼしません。

**消したことも配ります。** ルールを消すと行が消えるので、そのままでは
次の同期で「そんなものは無かった」ようにしか見えず、**別の端末が送り返してきて
生き返ります。** 墓標を残して、消したこと自体を配ります(90日で掃除)。

**アプリ名を別に配る**のは、実績に `com.twitter.android` や `chrome.exe` しか
入っていないためです。名札が無いと、別の端末の実績を読める形で出せません。
鍵を `android:` `windows:` で分けてあるのは、`chrome.exe` のように
両方に存在しうる名前で**互いに上書きし合わない**ようにするためです。

**実績は端末ごとに分けて持ちます。** 合算で上書きすると
「スマホ30分 + PC20分」の日が 20分になります。

> Windows 側が送るのは**今日ぶんだけ**です。使用の記録を48時間しか持っていないので、
> 持っていないものを 0 として送ると**サーバー上の過去を 0 で塗り潰します**。

## ルールの持ち出しと取り込み

**ルール → 書き出す** で、いまのルールを JSON 1つに落とせます。
**読み込む** で戻せます。Android(設定アプリのファイル選択)でも Windows でも同じ形式です。

### なぜ目録を同梱するのか

条件は `"typeId": "time_range"` のような文字列で保存されています。ルールだけを書き出すと、
受け取った側からは**どんな条件が在って、どの値をどの名前で渡すのかが分かりません**。
当てずっぽうで書けば、取り込みで弾かれるか、もっと悪いことに
「どこにも当たらないルール」になります。

なので書き出しには `catalog` を添えてあります。いま登録されている条件・アクション・
サイトの束が、既定値と範囲つきで全部入っています。
**このファイル1つ渡せば、外の道具が正しいルールを書けます。**

```jsonc
{
  "format": "dopachiru.rules",
  "rules": [ /* ここを足したり書き換えたりする */ ],
  "catalog": {
    "conditions": [ { "id": "time_range", "params": [ { "key": "start", "type": "timeOfDay", ... } ] } ],
    "hints": [ "timeOfDay と minutes は分で書く。23:00 は 1380、6:00 は 360。", ... ]
  }
}
```

### 雑に書いても通る

外で書いたルールは、パラメータを全部は埋めていないのが普通です。
**書き漏らした欄は既定値で埋めます** ── 抜けを理由に丸ごと捨てると、
惜しいところまで書けたルールが無駄になります。

弾くのは、直さないと**効かないルールになる**ものだけです。

| 弾くもの | なぜ |
|---|---|
| 知らない条件・措置の ID | 評価できないので、入れても動かない |
| 対象が空 | 何にも当たらない。入っていても効かない |
| URL の書き方が違う | 止めているつもりで止まらない |

1件おかしくても、残りは取り込みます。

### 取り込みも変更ゲートを通ります

押した瞬間には何も変わりません。**何件増えて何件差し替わるかを先に見せます。**
新しく増えるぶんは即時、既存の差し替えはゲートを設定してあれば申請になります ──
ファイルを1つ読ませるだけで縛りを緩められるなら、ゲートを置いた意味がありません。

`uid` が同じルールは差し替え、違えば追加です。差し替えでも端末内の番号は保つので、
罰や記録の紐付けは切れません。

## URL でページを止める

ブラウザは1つのアプリなので、プロセス名では「YouTube のショートだけ」が書けません。
ルールの対象に **URL** を足してあります。

書き方は `ホスト` か `ホスト/パスの先頭` だけです。正規表現は受け付けません
── **書き間違いが「どこにも当たらないルール」になって静かに効かなくなる**のが、
止めているつもりで止まっていない状態を作るからです。

| 書いたもの | 当たる | 当たらない |
|---|---|---|
| `youtube.com` | youtube.com のすべて | それ以外 |
| `youtube.com/shorts` | `/shorts` と その下 | `/watch`, `/shortstack` |
| `tiktok.com` | `www.` `m.` などの下位ドメインも | `nottiktok.com` |

除外(`exceptSites`)は全指定にも効くので、「ブラウザは丸ごと止めるが
Google ドキュメントだけ通す」が書けます。罰の封鎖もサイト単位で科せます。

`SiteCatalog` によく挙がるサイトの束が4つ入っています。
**短い動画をサイト全体と分けてある**のは、「YouTube は調べ物に要るが、
ショートだけ止めたい」がいちばん多い形だからです。

判定を動かすには Chrome 拡張が要ります → [extension/README.md](extension/README.md)

## Windows 版

`:desktop` モジュール。Kotlin + Compose Desktop で、**ルールエンジンは Android と同じ
`:core` をそのまま使います**(`core` には Android の import が1つも無く、
`java.time` と kotlinx.serialization だけで動く)。移植で書いたのは
「前面のアプリを Win32 から拾う」「判定の結果を Windows のやり方で実行する」の2つだけです。

```bash
gradlew :desktop:run
```

### できること

タブは **ルール / タグ / 変更 / 今日 / 設定** の5つで、スマホ側とほぼ同じことができます。

| | Windows | 備考 |
|---|---|---|
| ルールの対象を選ぶ(アプリ・タグ・URL・全部) | ○ | 動いている exe から選ぶか、名前を直接足す |
| 条件(AND / OR / NOT のかたまり) | ○ | Android と同じ編集画面 |
| 措置(封印・警告・遅延・音だけ・目的・閉め出し) | ○ | |
| 破ったら(封鎖・ポイント) | ○ | |
| タグを付ける | ○ | |
| 関門つきのルール変更 | ○ | 待つ・理由を書く・時間帯の3つ |
| 端末間の同期 | ○ | ルール・タグ・アプリ名・1日の使用時間 |
| 集中モード / 予約 | ○ | 範囲(グループだけ/以外/全部)も選べる |
| アプリ内の画面判定(ショート・リール) | **×** | Windows には見分ける手立てが無い。ブラウザは URL で取れる |
| ホーム画面のショートカット | **×** | Windows に相当するものが無い |

> **閉じているアプリも指定できます。** Windows には「インストール済みアプリ」の統一された
> 一覧が無いので、一覧に出るのは**いま窓を持って動いているもの**だけです。止めたいゲームを
> 起動しなくても設定できるよう、実行ファイル名(`aces.exe` など)を直接足せます。

配布物は2種類。どちらも JRE を同梱しているので、Java を入れていない PC でも動きます。

```bash
gradlew :desktop:packageSetup      # dist/dopachiru-windows-<版>-setup.zip(WiX 不要)
gradlew :desktop:distMsi           # dist/dopachiru-windows-<版>.msi(WiX 3 が要る)
gradlew :desktop:packagePortable   # dist/dopachiru-windows-<版>.zip(持ち運び版)
```

| | 入れ先 | 管理者権限 | 自動起動 | 要るもの |
|---|---|---|---|---|
| `packageSetup` | `%LOCALAPPDATA%\Dopachiru` | 不要 | 使える | なし |
| `distMsi` | `%LOCALAPPDATA%\Dopachiru` | 不要 | 使える | WiX 3 |
| `packagePortable` | 展開したところ | 不要 | 使える(注) | なし |

`packageSetup` は app イメージに `install.cmd` を添えて固めたもの
([desktop/packaging/](desktop/packaging/))。展開して `install.cmd` を叩くと、
`%LOCALAPPDATA%` に置いてショートカットを作り、「アプリと機能」にも登録します。
アンインストールもそこからできます。設定と記録(`%APPDATA%\dopachiru`)は消しません。

> **MSI には WiX 3 が要ります**
> jpackage が `candle.exe` / `light.exe` を呼ぶためで、Gradle は落としてくれません。
> WiX 4 以降では**動きません**(jpackage が対応しているのは v3 まで)。
>
> ```
> winget install --id WiXToolset.WiXToolset -e
> ```
>
> 入れたあとはターミナルを開き直してください(PATH が通るのが新しいセッションから)。

> **1.0.x の MSI を入れたままの場合**
> 1.0.x は端末全体に入る版でした。入れ替えではなく**別物として並んで入る**ので、
> 先に「アプリと機能」から古いほうを消してください。

持ち運び版は展開して `Dopachiru\Dopachiru.exe` を叩くだけ。
(注)自動起動はレジストリに**そのときの置き場所**を書くので、フォルダを動かすと
効かなくなります。動かした先で一度起動すれば書き直されます。

### ルールを変えにくくする(関門)

設定 → 関門 で置きます。1つでも置くと、ルールの**変更と削除**はその場で効かなくなり、
「変更」タブで全部通してから適用されます。**新しく作るぶんは素通り**です ──
縛りを増やすほうを渋らせる理由が無いし、渋らせると「まず緩めてから作り直す」を覚えます。

| 関門 | 通しかた |
|---|---|
| 起票から待つ | 時間が経つだけで通る(既定1時間) |
| 理由を書かせる | 決めた文字数以上書く。文は履歴に残る |
| 決まった時間帯だけ | その時間帯に入れば通る(既定 8:00〜21:00) |

**これが無いと、開きたくなった瞬間にルールを消せます。** 2秒で外せる縛りは縛りになりません。
Windows で出しているのはこの3つだけで、パスワードとミニゲームは置いていません ──
こちらに通す手立てが無いものを並べると、出口の無い檻になるためです。
関門は**端末ごと**で、同期しません(片方で出した申請をもう片方で承認できてしまうため)。

### Windows と一緒に立ち上げる

設定 →「Windows と一緒に立ち上げる」で入れられます。実体は
`HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run` の1行で、
管理者権限は要りません。ログインで立ち上がったときは `--startup` が付くので、
**窓を出さずトレイだけ**で始まります。

タスクマネージャの「スタートアップ アプリ」にも並ぶので、そちらからも切れます。
切られていることは設定画面にも出ます(Windows は切っても Run の行を消さないため、
アプリ側で見ないと「入れたのに立ち上がらない」の理由が分からなくなる)。

> **MSI を作るときの注意**
> `nativeDistributions` の `description` に日本語を入れると、WiX の `light.exe` が
> 311 で落ちます(`-cultures:en-us` で処理されるため)。ここだけ英語にしてあります。

Win32 まわりが実機で動くかの確認:

```bash
gradlew :desktop:win32Smoke
```

### Android との違い

| | Android | Windows |
|---|---|---|
| 対象の識別 | パッケージ名 | 実行ファイル名(`chrome.exe`) |
| 前面の検知 | ユーザー補助のイベント(即時) | `GetForegroundWindow` を1秒おき |
| ブロック画面 | `TYPE_ACCESSIBILITY_OVERLAY` | 最前面・枠なし・全画面の普通のウィンドウ |
| 保存先 | Room | `%APPDATA%\dopachiru\*.json` |
| 常駐 | AccessibilityService | タスクトレイ |

### ブロックのやり方を選べる

Windows には Android のような統一された止め方がないので、設定タブで選びます。

| | 内容 |
|---|---|
| オーバーレイのみ | 最前面に全画面の窓を出すだけ。Alt+Tab や仮想デスクトップで裏に回れる余地が残る |
| 最小化し続ける(既定) | 加えて対象のウィンドウを最小化し続ける。戻してもまた最小化される |
| プロセスを一時停止 | `NtSuspendProcess` で対象を凍らせる。最も強いが、保存していない編集内容を壊すことがある |

一時停止は、止めた pid を必ず控えて終了フックで戻します。
**ドパチルが落ちても、巻き添えでプロセスが固まったままにはなりません。**

`explorer.exe`・`taskmgr.exe`・ログオン関係・ドパチル自身は、ルールより強く常に除外します
([`ProtectedProcesses`](desktop/src/main/kotlin/com/dopachiru/desktop/platform/ProtectedProcesses.kt))。
タスクマネージャを入れてあるのは、ドパチル自身を必ず止められるようにしておくためです。

## 制限条件を1つ増やす

このアプリは「思いついた制限をどんどん足せること」を最優先に組んであります。
**新しい条件を足すのに触るファイルは2つだけ**で、UI 側には手を入れません。

### 1. 条件の実装を1ファイル書く

`core/src/main/kotlin/com/dopachiru/core/condition/types/` に置きます。

```kotlin
/** 充電中かどうかで成立する条件の例 */
object ChargingCondition : ConditionType {
    const val KEY_WHILE_CHARGING = "whileCharging"

    override val id = "charging"                  // 一度決めたら変えない
    override val displayName = "充電中"
    override val description = "充電しているあいだ(またはしていないあいだ)に成立する。"

    override val params = listOf(
        ParamSpec.BoolParam(KEY_WHILE_CHARGING, "充電中に成立させる", default = true),
    )

    override fun evaluate(p: Params, ctx: EvalContext): Boolean =
        ctx.charging == p.bool(KEY_WHILE_CHARGING, true)

    override fun summarize(p: Params): String =
        if (p.bool(KEY_WHILE_CHARGING, true)) "充電中" else "充電していないあいだ"
}
```

### 2. `DopaCore.registerAll()` の一覧に足す

```kotlin
ConditionRegistry.register(
    AlwaysCondition,
    TimeRangeCondition,
    // ...
    ChargingCondition,   // ← これだけ
)
```

これで完了です。設定画面の「条件を足す」に出てきて、`params` に書いた項目の
入力欄も自動で生えます。永続化スキーマ(Room のテーブル)も変わりません。

### 電池のために `nextChangeAt` も書く(任意)

条件は「この時刻までは成否が変わらない」を答えられます。

```kotlin
override fun nextChangeAt(p: Params, ctx: EvalContext): LocalDateTime =
    ctx.now.plusMinutes((p.int(KEY_MINUTES) - ctx.usage.currentSessionMinutes).toLong())
```

答えられたぶんだけ、アプリはその時刻まで一度も起きません。
**書かなくても正しく動きます** — 実装しなければ「分からない」扱いになり、
呼び出し側が安全側に倒して短い間隔で見に来るだけです。

### 判定に新しい情報が要るとき

上の例の `ctx.charging` のように、既存の [`EvalContext`](core/src/main/kotlin/com/dopachiru/core/engine/EvalContext.kt)
に無い情報が必要なら、そこにフィールドを1つ足して `DopaRuntime.decide()` で埋めます。
既存の条件は読まないので影響しません。

### 入力欄の種類が足りないとき

[`ParamSpec`](core/src/main/kotlin/com/dopachiru/core/param/ParamSpec.kt) に種類を足し、
[`ParamEditor`](app/src/main/kotlin/com/dopachiru/ui/rules/ParamEditor.kt) の `when` に
描画を1本足します。ここだけは UI に触ります。

**アクションを増やす場合も同じ手順です**(`ActionType` を書いて `ActionRegistry` に登録)。
ただしアクションは画面表示を伴うので、`DopaAccessibilityService.present()` に
分岐を1本足す必要があります。

## 研究知見から入れたもの

[digital-wellbeing-research.md](digital-wellbeing-research.md) のまとめを反映した部分。
根拠は各クラスの KDoc に、出典つきで書いてあります。

### なぜ「遅延」を足したか

367個の自己制御ツールを二重過程モデルで分類した調査(Lyngs ら CHI 2019)で、
**ブロックは74%が実装しているのに、遅延を扱うものは4%しかなかった**。
自己制御の成否は「報酬の大きさ・成功見込み・**報酬までの遅延**」で決まるので、
遅延は理論的には中心にあるのに、実装だけが空白でした。

`delay` は押し切りボタンを置いていません。**必ず通る**ので拒まれた感覚が生まれず、
それでも反射で掴んだ手は一度止まります。入力に微細な妨害を入れた研究では、
従来のロックアウトに対して**削減 追加15.6% / 受容度 +25.3%** でした。

### なぜ「確率」と「文の入れ替え」があるか

固定の介入は**露出1日ごとに効果が25%落ちます**(HabitLab)。27種を回すと -34%/日。
毎回の摩擦は **53%が苛立ち、33%が継続意欲を下げた**(Design Frictions 2024)。

- `chance` — たまにだけ発火させる。同じ使用のあいだは答えが変わらないので、
  ブロックが数秒おきに出たり消えたりしない
- 反省文・待ち時間の文は**改行で分けると1つずつ選ばれる**。
  回しているときは「同じ言葉だと慣れるので、毎回変えています」と画面に添える
  ── 理由を説明しないローテーションは残存率を 68%→39% に落とし、
  **説明すると 80% に戻る**

### なぜ押し切りに手間が要るか

GoalKeeper(IMWUT 2019)で、**警告ダイアログの92%は「使い続ける」で無視されました**。
1タップで通れるものは、事実上そこに無いのと変わりません。
`block` の「押し切るのに要る手間」で、3秒長押しか言葉の打ち込みを要求できます。
手間で諦めさせるのが狙いではなく、**意識のほうを一度起こす**のが狙いです。

### なぜ段階的に強くするのか

同じ研究で、強度3水準を比べた結果:

| | 削減 | 選好 |
|---|---|---|
| 通知のみ | -32.1分/日(有意差なし) | 33.3% |
| **段階的ロック**(1→5→15→30→60分) | **-50.4分/日** | **52.8%** |
| 強制ロック(超過で深夜まで) | -73.7分/日 | 13.9% |

強制が強いほど**目標そのものを緩めます**(強条件では20名が上方修正、弱条件では5名)。
`habituation` 条件と `lockEscalates` は、この「最初は軽く、効かなくなってから強く」を
組むためのものです。

### 雛形は弱い順に並べる

依存傾向が高い群の**41.7%が最弱の介入を選好**しました。
最も助けが要る人が最も強い介入から降りるので、強いものを既定にしていません。
雛形の一覧は「まず軽いものから → 上限を決める → 開く癖を狙う → 強く縛る」の順で、
それぞれになぜ効くのかを添えてあります。

### 入れていないもの

| 研究にあるが入れていない | 理由 |
|---|---|
| 金銭ペナルティ(達成率 79.9% vs 9.83%) | 効果は桁違いだが、資金決済法・ストア規約・依存傾向のある人への倫理を先に確認する必要がある |
| 進捗の公開・共有(d+ 0.19 → 0.55) | サーバーが要る。同期の実装が先 |
| 機能単位の制限(YouTubeのショートだけ等) | Accessibility 経由になり Play の規約リスクが高い。ブラウザ拡張のほうで先に試す |
| グレースケール(-20分/日, d=0.51) | 端末全体の色を変える権限が取れない |
| 気分・眠気による切り替え | 入力を求める仕組み(ESM)が要る。まずログだけで測れるものから |

### 自己監査

この研究まとめ自身が「あなたのアプリが ACDP に転落していないか」を問うています。
いまの作りに対する答え:

- **ストリークが「使わないと失う」になっていないか** → 連続記録は途切れても罰しません。ポイントの下限もあります
- **ポイント集めが Grinding になっていないか** → ポイントは貯めること自体が目的にならないよう、使い道は逃げ道を買うことだけです
- **アンインストールが困難になっていないか** → 設定から無効化する経路は必ず通ります(一拍置くだけ)
- **失敗を責める設計になっていないか** → 加点は「引き返した」「違反ゼロで終えた」「完走した」の3つで、
  可視化するのは成功のほうです

## 条件の組み立て(AND / OR / NOT)

条件は木で持っていて、**かたまり**を入れ子にできます。編集画面ではかたまりごとに
「すべて満たす(AND)/ どれか満たす(OR)」を切り替え、各項目に「〜でないとき(NOT)」の
札を付けます。括弧を数えなくても、どこまでが一組かが見えるようにするためです。

```
すべて満たす
 ├ 夜のあいだ 22:00〜06:00
 └ どれか満たす
    ├ 連続15分
    └ 今日10回目
```

- 入れ子は **2段まで**。3段目からは画面の横幅で括弧の対応を追えなくなるので、
  そこまで深い式が要るならルールを2つに分けたほうが後から読めます。
- 否定は木の上では `Not` の入れ子ですが、画面では札として見せています。
  使う側にとっては「この条件をひっくり返す」以上の意味が無いため。
- 一覧には木を1行に畳んだ説明が出ます(`ConditionTree.describe`)。

木を組み替える道具は `core` の `ConditionTree` にあり、Android と Windows で同じものを使います。

## 破ったらどうなるか(罰とポイント)

アクションが「その場で何を出すか」なのに対し、**罰は押し切ったあとに効きます**。
ルールごとに設定します。

### 「どうする」と「破ったら」は別の軸

ここを取り違えると設定が意味不明になるので、はっきり分けておきます。

| | 何を決めるか | いつ効くか |
|---|---|---|
| **どうする**(措置) | 開こうとした瞬間に出すもの(封印・警告・遅延・音だけ・目的を書く・閉め出す) | その場 |
| **破ったら**(報い) | それを振り切って使ったあとに来るもの(封鎖・ポイント) | そのあと |

**破れない措置に罰は付きません。** 完全封印の「押し切って使えるようにする」を切ると
破る道が無くなるので、罰の欄は丸ごと死にます。編集画面はこれを見て、効かない欄は
出さずに「この措置は破れない」とだけ書きます(`RuleCheck.isBreakable`)。

> **「条件を満たすあいだ開けない」だけが欲しいなら**、完全封印を選んで
> 逃げ道を「押し切れない」にします。罰も条件の作り込みも要りません。

### 何をもって「破った」とみなすか

| 場面 | 判定 |
|---|---|
| ブロックを押し切った | その場で |
| 宣言した時間を超えた | 超えた時点で(1回の宣言につき1度だけ) |
| 警告を無視して使い続けた | 警告から N 分(既定5分)経っても同じアプリにいたら。**そのアプリを離れるまで1度だけ** |

警告の3つめを「出るたび」にしないのは、繰り返し警告が出る設定だと
1時間ほどで残高が下限に張り付き、そこから何をしても押し切れなくなるためです。

### 封鎖(お預け)

| 範囲 | 閉まるもの |
|---|---|
| 封鎖しない | ポイントだけ動く(既定) |
| そのアプリだけ | 破ったアプリ1つ |
| このルールの対象ぜんぶ | タグで括っていればグループ単位 |
| 逃がすもの以外ぜんぶ | 選んだアプリ以外、端末全体 |
| 選んだものだけ | ルールの対象とは**別に**選んだアプリ・タグ |

最後の1つは「Twitter を押し切ったら SNS のタグごと閉める」のように、
**破ったものと閉まるものを別にしたい**とき用です。上の3つはどれも対象から
自動で決まるので、この書き方だけができませんでした。選び忘れ(空のまま)は
「全部」ではなく**何も閉めない**に倒します。

- 閉まるあいだは**押し切る手段がありません**。あるのは残り時間だけ。
- 上限は **12時間**。桁を間違えて一日詰むことがないようにしてあります。
- 電話・ホーム・設定・キーボード・ドパチル自身は、罰の最中も必ず使えます
  (`ProtectedApps` / `ProtectedProcesses`。ここは設定から外せません)。
- 範囲は**罰を科した時点で固定**されます。あとからルールを書き換えても、
  すでに科した罰の重さは変わりません。
- 再起動しても残り、時刻が過ぎれば誰の手も借りずに解けます。

### ポイント

守ると貯まり、破ると減ります。使い道は設定で選べます(両方切ると「数えるだけ」)。

| 使い道 | 内容 |
|---|---|
| 押し切りの代金 | 押し切るのにポイントが要る。足りなければボタンが押せない |
| 解禁券 | ポイントで「N分だけ制限が全部止まる」券を買う |

- 増減はルールごとに設定でき、「設定どおり」にしておけば全体の相場が効きます。
- **下限**があります(既定 -100)。際限なく沈むと、そこから何をしても
  押し切れないまま「もうどうにでもなれ」に振り切ってしまうため。
- **解禁券では罰は解けません。** ポイントで買えるのはルールの免除であって、
  科された罰の時間ではありません。ここを通すと、罰が「もっと払えば消える」ものに
  変わり、封鎖画面の「押し切る手段はありません」が嘘になります。
- 加点は「引き返した」「違反ゼロで一日終えた」「学習予定を完走した」の3つ。
  中断した予定は完走に数えません。

判定の順番は `RuleEngine.decide` の1か所に置いてあります: **罰 → 解禁券 → ルール**。

## 設計上の判断

### オーバーレイに `TYPE_ACCESSIBILITY_OVERLAY` を使っている

`SYSTEM_ALERT_WINDOW` (`TYPE_APPLICATION_OVERLAY`) ではなく、AccessibilityService から
出せる `TYPE_ACCESSIBILITY_OVERLAY` を主に使っています。理由は3つ:

1. **ナビゲーションバー・ステータスバーの上に出せる** — `TYPE_APPLICATION_OVERLAY` は出せない
2. **Android 12 以降のタッチ透過制限を受けない** — 「警告表示」で下のアプリを操作させ続けられる
3. SYSTEM_ALERT_WINDOW 権限が要らない

詳細は [`risk-assessment.md`](risk-assessment.md) の A-1 を参照。

### Foreground Service は検知の前提ではない

AccessibilityService はシステムがバインドし、端末の再起動もまたいで有効なままです。
`MonitorService` の役割は「プロセス優先度を上げる」ことと「使用時間を1分ごとに刻む」ことだけです。

Android 14 以降 `foregroundServiceType` が必須なので `specialUse` を宣言しています。
これは Google Play 配布時のみ審査対象で、サイドロードなら審査は発生しません。

### 変更抑制は「緩める方向」にだけかかる

新規作成と有効化は即時反映、変更・削除・無効化はゲートを通します。
縛りを増やす方向に摩擦をかけても意味がないためです。

ゲートは6種類。組み合わせて使えます。既定は「30分待つ + 理由を30文字」。

| ゲート | 内容 |
|---|---|
| `cooldown` | 起票から一定時間置く。時間の経過だけで自動的に通過 |
| `writeReason` | なぜ変えたいかを書かせる。書いた内容は履歴に残る |
| `miniGame` | 計算問題を N 問。途中で間違えると最初から |
| `password` | パスワード(PBKDF2-HMAC-SHA256 / 12万回) |
| `timeWindow` | **曜日と時刻**の窓。日をまたぐ指定も可(例: 金 22:00〜02:00) |
| `calendarWindow` | **カレンダーに特定の予定があるあいだだけ**変更できる(凍結中は常に開く) |

`cooldown` / `timeWindow` / `calendarWindow` は状況で自動判定されるので、
条件を満たせば勝手に通過し、外れればまた塞がります。
`calendarWindow` は「#可変」という予定を自分で先に入れておく使い方を想定していて、
予定を入れる行為そのものが事前のコミットメントになります。

### カレンダー連携は凍結中(2026-08-15〜)

連携相手のスキマスが完全ローカルになり、学習予定はブロードキャストで直接届くように
なりました([INTEGRATION.md](INTEGRATION.md))。カレンダーを経由する理由が無くなったので、
読みに行くのをやめています。

凍結の switch は `core` の `DopaFeatures.CALENDAR_ENABLED` 1か所です。

| | 凍結中 |
|---|---|
| 端末のカレンダー | 一切読まない。`READ_CALENDAR` は**マニフェストの宣言ごと外してある** |
| `calendar_busy` 条件 | 常に成立しない |
| `Gate.CalendarWindow` | 常に通過扱い |
| 条件・ゲート・雛形の選択肢 | 出ない |
| 保存済みのルール | 残る。編集画面に「凍結中」と出る |

**条件とゲートで倒す向きが逆**なのが肝です。素直に「カレンダーは空」として扱うと、

- 「予定が**無い**あいだ封印」(`duringEvent = false`)が永久に成立して端末が閉まりっぱなしになる
- 「予定中だけ変更できる」の関門が永久に閉じて、ルールを一生直せなくなる

の両方が起きます。どちらも「止めた機能が、止めたせいで人を縛る」形なので、
条件は成立しない側に、ゲートは開く側に倒しています。`CalendarFreezeTest` で押さえています。

戻すときは `CALENDAR_ENABLED` を `true` にして、マニフェストの `READ_CALENDAR` を
生かす2箇所だけです。

<details>
<summary>凍結前の作り(戻すときの参考)</summary>

Google Calendar API も OAuth も Google Cloud のプロジェクトも使っていません。
**Google カレンダーは端末に同期された時点で標準のカレンダー Provider に入る**ので、
`READ_CALENDAR` のランタイム権限を1つ取るだけで、同期済みの全アカウントの予定が見えます。

- 通信が発生しないので、予定の内容が端末の外に出ない
- トークンの失効やリフレッシュを考えなくてよい
- Google 以外のカレンダー(Exchange など)も同じ経路で読める

終日予定は UTC の 0:00 で入っているので、端末のローカル日に読み替えています。

</details>

### タグでアプリをまとめる

「SNS」「動画」のようにアプリをまとめ、ルールの対象をタグで指定できます。
あとから対象アプリを増やすとき、タグに1つ足すだけでそのタグを使う全ルールに効きます。
タグ画面から作成・メンバー編集・削除ができます。

### アプリを選ぶ画面

対象・除外・タグのメンバーは、どれも同じ一覧
([`AppPickerList`](app/src/main/kotlin/com/dopachiru/ui/common/AppPicker.kt))で選びます。
アイコン付き、検索、並べ替え3種(名前順 / 使用時間 / 選択中が上)。

名前順は `Collator`(日本語)を通しているので **ABC → あいうえお** の順になります。
単純な文字コード順だとカタカナと平仮名が離れ、濁点付きが妙な位置に来ます。
ただし**漢字だけは読みではなく文字コードで並びます**(読みは端末から取得できないため)。

使用時間は端末の使用状況から直近1週間ぶんを読みます
([`AppUsageRanking`](app/src/main/kotlin/com/dopachiru/data/AppUsageRanking.kt))。
**ドパチルを入れる前の実績も見える**ので、最初にルールを作るときに効きます。
許可(設定 → 特別なアプリアクセス → 使用状況へのアクセス)が無いときは、
ドパチル自身の記録(48時間ぶん)に落ちます。どちらも無ければ名前順に落ちるだけです。

### 対象は「選んだものを止める」と「選んだもの以外を止める」の両方

`Target` は二通りの書き方ができます。

- **正指定** — パッケージとタグの和。「この5個を止める」
- **全指定** — `matchAll` を立てて、例外を `exceptPackages` / `exceptTags` に置く。
  「必要なもの以外ぜんぶ止める」= 許可リスト型

除外は正指定より常に強いので、「タグで広く取って数個だけ抜く」という書き方もできます。

### 何があっても止めないアプリ

電話・ホーム・設定・キーボード・ドパチル自身は、どのルールからも制限されません
([`ProtectedApps`](app/src/main/kotlin/com/dopachiru/data/ProtectedApps.kt))。

**これはルールより強く、設定画面からも外せません。** 許可リスト型を入れるまでは、
電話を封印するには電話アプリをわざわざ選ぶ必要があったので事故になりませんでした。
「必要なアプリ以外ぜんぶ」が書けるようになった時点で、選ばなくても巻き込めるようになります。
この床はその対です。設定に置けば、いつか間違って外せてしまうので置いていません。

### 電池

常駐アプリなので、消費を抑える設計をいくつか入れています。

**一定間隔のポーリングをやめた** — 判定は毎回「次はいつ見に来ればよいか」を条件に聞き、
そのぶんだけ眠ります。「連続15分で警告」なら、開いた直後は15分後まで一度も起きません。
時刻の計算ができない条件(カレンダーなど)が混じったときだけ、安全側に倒して短い間隔に戻ります。

**そもそも動かさない条件** — 次のときは判定を完全に止めます。

- 画面が消えているあいだ
- 前面のアプリを狙っているルールが1つも無いとき
- ホーム画面・設定アプリにいるとき

**それ以外**

- カレンダーは、それを使うルールかゲートがあるときだけ、5分おきに読む(既定では読まない)
- 使用時間の DB 書き込みは、値が実際に動いたときだけ
- ユーザー補助の設定から `flagRetrieveInteractiveWindows` と `flagIncludeNotImportantViews` を外した。
  どちらもシステムにノードツリーを余分に組ませるが、このアプリは `rootInActiveWindow` しか使わない

設定タブの「電池を優先する」をオンにすると、間隔がさらに伸びます
(ブロックが最大2分遅れることがある代わりに消費が減る)。

> **画面オフ中の計測について**
> 画面が消えたらセッションを明示的に閉じています。閉じないと寝ているあいだの時間が
> まるごとアプリの使用時間になり、宣言した持ち時間も勝手に減っていきます。

### 自分から守る(任意)

設定アプリでドパチルのページを開いたとき、連続日数を見せて10秒だけ引き止めます。
既定はオフ。設定タブから有効にできます。

**無効化そのものは必ずできるようにしてあります。** 自分で入れたアプリを
自分で止められなくなるのは抑止ではなく事故なので、ここでやるのは一拍置かせることだけです。

### 待ち受け画面には重ねられない

ロック画面は OS が最上位で保護しているため、オーバーレイを被せられません。
代わりに **ロック解除の直後**に問いかけを出しています(設定でオフにできます)。
